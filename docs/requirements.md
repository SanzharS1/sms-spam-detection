# Functional and Non-Functional Requirements

## 1. Purpose and scope

This specification defines the intended behavior and quality constraints of **Development of a Web-Based SMS Spam Detection Application Using Machine Learning**. It refines the [Project Proposal](project_proposal.md), particularly objectives O-01–O-08 and Sections 9–18, for a service that checks manually submitted English, Russian and Kazakh SMS. Intended users include public checker users, authorized history owners and restricted feedback/model operators. Their needs remain hypotheses until supported by DIP-2 evidence.

The first pre-defense deliverable is a traceable requirements specification prepared for team review. The requirements below describe the final system and its future acceptance tests; they do not establish completed implementation, experiments or user validation. An initial English demonstrator may precede RU/KZ evaluation without removing multilingual work, batch checking, history, feedback or deployment from the final scope.

Automatic inbox access, carrier blocking, paid SMS gateways, opening message links, executing attachments, guaranteed fraud prevention and unrestricted online learning are outside scope. A prediction never certifies a sender, URL or message as safe.

### 1.1. Conventions and priorities

- **Shall** expresses a requirement. **Must** denotes a final-scope capability, essential correctness/privacy constraint or mandatory evaluation-evidence obligation. Failure blocks acceptance of the affected capability or evaluation claim.
- **Should** denotes a useful refinement that can be deferred with a recorded rationale while preserving the mandatory workflow. **Could** denotes an optional enhancement. No Could requirements are introduced in this baseline.
- Priorities are proposed from the documented project scope, rather than confirmed user preferences. DIP-2 and substantive supervisor review may revise them through a documented decision. Must does not mean implemented for the first pre-defense.
- **Pending** identifies an unresolved contract or parameter. A specification review can establish that its owner and verification method are identified; it cannot establish system compliance. Tests depending on an unset parameter remain blocked, never passed by assumption.
- EN/RU/KZ are display names; message-language codes follow the dataset strategy: `en`, `ru`, `kk`, `mixed`, `und`, `other`. Interface language, message-language evidence and evaluated model coverage are distinct.
- `spam` and `ham` are the only classifier labels. Annotation workflow states such as uncertain or unusable are not additional model classes. A model-estimated probability is not automatically calibrated confidence.

All acceptance criteria specify future observations and required evidence. Synthetic fixtures are suitable for contract/security checks; model-quality claims require permitted labeled evaluation data. No test outcomes are asserted here.

## 2. Stakeholders, boundaries and responsibilities

The public checker user submits selected text without inbox access. An authorized history/session owner may inspect only their permitted records. A feedback reviewer may assess corrections and permitted contributions; the model/evaluation maintainer controls offline training and candidate evaluation. An operator manages deployment, secrets, health and recovery. These are proposed permission roles, not confirmed accounts or evidence of recruitment. Public users cannot grant themselves review or promotion rights.

The planned component boundary is React/TypeScript UI -> FastAPI contract/authorization -> compatible inference -> versioned result, with PostgreSQL for permitted metadata and separate restricted artifact/data storage. These choices follow the [backend/storage comparison](technology_comparison.md); selecting them does not itself satisfy security or performance requirements. Endpoint paths, transport schemas, session mechanism and database schema await architecture/contract review.

- **Sanzhar Sabyrov** leads inference, explanations, threshold/error analysis, FastAPI contracts, validation, privacy/masking, rate limiting, history persistence/API, Docker, CI, deployment and API integration tests. He coordinates this specification and supports data cross-labeling, UI integration and feedback schema/processing.
- **Beknur Serikkali** leads data preparation, cleaning/deduplication, annotation/agreement, character-feature experiments, React/TypeScript, batch and multilingual UX, history/statistics/feedback screens, accessibility and usability. He leads documentation/report assembly and contributes API agreement, component tests and clean-machine checks.
- **Rafael** leads TF-IDF training/evaluation, algorithm comparison, cross-validation, held-out metrics, model selection/versioning, history/statistics/feedback behavior, confirmed-feedback retraining and general unit/E2E/load/adversarial testing. He reviews data partitions, explanation clarity and backend/UI/deployment and writes the Results chapter.

Each member writes documentation and tests for their components. Assigned responsibilities below describe planned ownership, not completed authorship or review. Final contract and model decisions require the relevant owners' actual review.

## 3. Functional requirements

| ID | Priority | Required behavior | Observable acceptance criterion and evidence |
|---|---|---|---|
| FR-01 | Must | Accept a manually submitted single SMS through the UI and API. | Given a permitted, non-empty message within agreed limits, supported coverage and an available compatible model, submission produces one correlated prediction result. Failure cases are verified separately under FR-19 and do not count as successful classification. Contract/UI tests cover EN/RU/KZ text without reading an inbox; unevaluated cases follow FR-09. |
| FR-02 | Must | Return the selected model's binary classification. | For fixed compatible model fixtures, the API returns the expected fixture label, exactly `spam` or `ham`, and the UI displays the same label. Repeated fixed inputs use the documented deterministic inference configuration. Record fixture/model versions; fixture agreement does not establish real-world accuracy. |
| FR-03 | Must | Present probability, threshold and confidence meaning consistently. | A successful response carries a finite spam probability in [0,1], the effective threshold and documented decision rule, including equality handling. UI/API agree on the resulting class. Confidence wording identifies its method/validation limitations; no unvalidated score is described as calibrated or guaranteed certainty. Threshold, calibration and confidence mapping await D-03. |
| FR-04 | Must | Provide faithful explanation data with predictions. | On fixtures with independently checked feature contributions, explanation entries trace to actual features of the active pipeline and use the declared explanation method/version. No fixed suspicious-word list substitutes for model attribution. Unsupported explanation cases are disclosed rather than given fabricated reasons. |
| FR-05 | Must | Render explanations without misleading highlights. | UI tests verify that word/character contributions map to the intended visible spans after privacy transformation and normalization, including Kazakh letters and overlapping features. Protected spans are not exposed; missing mappings produce an explicit explanation limitation. Record expected offsets and reviewed examples. |
| FR-06 | Must | Accept batch files with an agreed CSV/UTF-8 contract. | A valid fixture containing quoted commas, embedded newlines and multilingual text produces one identifiable outcome per input record in the agreed order/mapping. Required columns, decoding and size limits follow D-04; arbitrary file types are rejected. A UTF-8 SMS record is not restricted to one physical line. |
| FR-07 | Must | Account for batch validation and partial failures. | For mixed valid/invalid rows, every parsed row has a result or explicit rejection with a stable row identifier; submitted/accepted/rejected counts reconcile. An unparseable file produces a file-level error instead of a misleading partial success. Retry/partial-processing behavior is fixed under D-04. |
| FR-08 | Must | Provide EN/RU/KZ interface selection. | Core entry, validation, result, batch, history and feedback states have reviewed text in each selected interface language. Switching UI language does not change the same model result or silently translate the SMS. Component tests exercise all three interfaces. |
| FR-09 | Must | Distinguish message language and evaluated coverage from UI language. | Given an unevaluated, mixed or undetermined case, the response/UI disclose the recorded coverage limitation and routing decision. UI choice alone cannot create a supported-language claim. D-03 defines when a result may be returned with a warning versus rejected as unsupported. |
| FR-10 | Must | Retrieve authorized prediction history. | With two independent owner/session fixtures, each can list and retrieve only its records; guessed identifiers and missing/expired authorization do not disclose another owner's record or existence details beyond the agreed error policy. Integration tests cover list and detail paths. |
| FR-11 | Must | Persist privacy-minimized prediction metadata. | Stored records contain an opaque identifier, authorized scope, time, class/score, threshold and model/preprocessing versions as agreed in D-02. Storage inspection finds no original SMS, sender details, full URLs or text-bearing explanation content in ordinary history. Prediction and persistence failures follow FR-19. |
| FR-12 | Must | Present authorized, model-aware history statistics. | Seeded metadata fixtures produce exact expected counts by class and model version within the owner's scope. Time/language filters, where used, expose their definitions. Predicted-spam counts are labeled as service statistics and never displayed as measured precision, recall or F1. |
| FR-13 | Must | Accept metadata-only incorrect-result feedback. | An authorized owner can flag a permitted prediction and optionally propose a label; the report receives a review state and correlated identifier. No SMS is retained or reconstructed as a side effect. Duplicate submissions follow the agreed idempotency rule; no live model changes. |
| FR-14 | Must | Separate text contribution from ordinary feedback consent. | Declining text-retention consent still permits metadata-only feedback. Accepting a separate notice records the permitted purpose and notice reference and initiates restricted intake/privacy review. A contribution without valid permission cannot enter a training release; contribution permission does not imply public redistribution permission. |
| FR-15 | Must | Restrict and record feedback review. | Public/owner roles cannot accept their own report as a verified training label. Authorized review records a decision, permitted evidence reference, reviewer identifier and time without overwriting original decisions. Unresolved/privacy-failed examples remain excluded; review fixtures follow the Annotation Guidelines' competence and independent-review rules. |
| FR-16 | Must | Retrain through a controlled offline process. | Only permission-cleared, privacy-reviewed, label-confirmed records enter a versioned training release. A reproducible run identifies data/splits/configuration and checks new examples against reserved evaluation groups. Public API requests and ordinary feedback do not start training or mutate the active model. |
| FR-17 | Must | Control candidate promotion, rejection and rollback using recorded evaluation evidence. | A candidate carries recorded evaluation evidence under D-03; only the authorized maintainer/operator can activate it after the agreed review gate. Failed compatibility/evaluation checks leave the previous active model unchanged. Promotion and rollback tests verify artifact, preprocessing and response-version agreement. |
| FR-18 | Must | Reject invalid or unsupported requests explicitly. | Empty/whitespace-only text, wrong types, malformed structures, invalid encoding, oversized input and unsupported formats produce documented validation outcomes before inference. Boundary tests use the agreed limits, including exactly at and beyond each boundary; no invalid row is silently dropped. |
| FR-19 | Must | Use consistent failure and retry semantics. | Validation, authorization, unsupported-model, overload and unavailable-dependency cases map to documented HTTP/error codes and safe messages. Responses include a correlation identifier and field/row references where appropriate, excluding submitted text and internal traces. Persistence failure is disclosed according to D-04; success never falsely promises saved history. |
| FR-20 | Must | Maintain an agreed UI/API/inference contract. | Schema/contract tests exercise single, batch, history and feedback requests with explicit allowed fields, types and errors. Output serialization excludes unauthorized/internal fields. The UI uses the same contract and renders results as text; no API route requires executing message content or following links. |
| FR-21 | Must | Apply compatible deterministic preprocessing. | Shared fixtures produce matching training/inference model input under the same preprocessing version. Unicode, placeholders, whitespace/case handling and explanation mappings follow the Dataset Strategy. Unsupported versions prevent model activation rather than triggering silent substitution. |
| FR-22 | Must | Identify the effective model and interpretation configuration. | Every successful single/batch-row result identifies the model, preprocessing, threshold and explanation/score-interpretation configuration. Stored history remains linked to the version actually used after promotion. Integration tests compare response, artifact manifest and persisted metadata, including rollback. |
| FR-23 | Should | Provide bounded navigation of authorized history. | For seeded histories exceeding one configured page, successive pages account for the permitted records under a documented ordering/snapshot rule without exposing another scope. Page size and navigation controls are agreed with Beknur; deferral cannot remove history or permit unbounded resource use. |

A documented data-flow inventory accounts for every temporary and retained copy; exceptions require separate permission and restricted access. |
| NFR-02 | Must | Mask sensitive content and keep errors/logs safe. | Agreed synthetic fixtures for URLs, emails, phone/account identifiers and sensitive spans pass the versioned transformation and negative log/error tests. | NFR-03 | Must | Isolate owner/session access. | D-02 defines credential/session lifecycle, expiry, revocation and ownership checks. Identifiers alone grant no authority; client-supplied owner fields cannot override authenticated scope. |
| NFR-04 | Must | Protect retained contributions and privileged operations. | The permission matrix separates public prediction, owner metadata, restricted text, review, training and promotion. Evidence/permission records are separated from ordinary history; least-privilege database access is verified. |
| NFR-05 | Must | Enforce retention, deletion and withdrawal rules. | D-05 supplies retention periods for metadata, intake, reviewed text, logs and recovery copies, plus withdrawal propagation rules. | NFR-06 | Must | Protect sensitive data in transit. | Deployment tests show the public UI/API uses HTTPS and credentials/SMS are not sent over cleartext paths. | NFR-07 | Must | Bound message, request and batch resources. | D-04 defines text length units, body/file bytes, row count, per-row and response bounds. | NFR-10 | Must | Fail safely and report partial outcomes accurately. | Fault injection for model loading, inference, database and artifact failures produces bounded documented responses without raw input, fabricated predictions or false persistence confirmations. | NFR-11 | Must | Support recoverable operation and rollback. | D-07 defines availability window, recovery-time/data-loss targets, health/readiness and recovery schedule. | NFR-12 | Must | Preserve multilingual Unicode semantics. | EN/RU/KZ, Kazakh-specific letters, Russian `ё`, emoji, mixed and transliterated fixtures survive agreed decoding/normalization and UI/API/storage round trips. | NFR-13 | Must | Provide accessible core interactions. | Keyboard-only tests can complete entry, batch submission, result interpretation, history and feedback without traps. | NFR-14 | Must | Provide responsive, readable workflows. | At viewports/device configurations agreed in D-08, core controls and results remain operable without hidden required actions or overlapping content. ## 5. API and ML interpretation rules

The following are proposed logical contracts rather than implemented endpoint definitions. D-04 will freeze field names, transport representations and HTTP/error mappings before implementation acceptance.

A prediction response must make the correlation/row identifier, binary label, spam probability, effective threshold and equality rule, confidence interpretation, explanation method, model/preprocessing versions and coverage limitations available to the UI. Probability and threshold must refer to the same score space. An absent calibration evaluation must be described as such; confidence categories must not be invented from arbitrary thresholds. Per-row failures must remain distinct from successful predictions and file-level failures.

History stores permitted metadata only. Text-bearing explanations can expose message fragments and therefore are not retained as ordinary history content. Returning an explanation transiently does not authorize saving it. A history item can be flagged without retaining the original text, but cannot reconstruct a training example from metadata or a hash. Text contributions use separate consent, restricted intake, privacy screening and confirmed labels. Feedback and model-promotion states are distinct from classifier output labels.

Data preparation and inference must share the agreed deterministic privacy/Unicode transformation, then use the trained feature extractor and estimator. The [Dataset Strategy](dataset_strategy.md) proposes masking before features, group-aware partitions and training-only learned transformations. Its 70/15/15 split, seed and feature settings are proposals for Rafael's review, not newly approved acceptance thresholds. The [Annotation Guidelines](annotation_guidelines.md) govern independent decisions, ambiguous cases and adjudication; an upstream label or public correction is not automatically confirmed ground truth.

Promotion must identify the evaluated artifact and its interpretation configuration. A database transaction alone does not atomically publish an external artifact or update all API workers. D-07 must define consistent activation, readiness and rollback so each response records the version actually used. Offline evaluation and retraining remain separate from public request execution.
