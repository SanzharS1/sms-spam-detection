# Verification and Evaluation Plan

This shared plan defines how achievement of the project's objectives will be demonstrated through testing, outcome measures, declared measurement conditions and comparison baselines. It supports university first pre-defense section 9 for **Development of a Web-Based SMS Spam Detection Application Using Machine Learning**. The API section below is a proposed verification design, not evidence of an implemented or evaluated application. The overall plan still requires separate ML and UX contributions.

## API Validation, Privacy, Security and Integration Testing

### 1. Scope, objectives and responsibilities

This section specifies the API-facing verification contribution for [DIP-11](https://sms-spam-se2425.youtrack.cloud/issue/DIP-11), prepared by Sanzhar Sabyrov. It follows the [Requirements Specification](requirements.md), [Architecture](architecture.md), [Project Proposal](project_proposal.md), [Technology Comparison](technology_comparison.md), [Dataset Strategy](dataset_strategy.md), [Annotation Guidelines](annotation_guidelines.md) and [Existing Systems Comparison](existing_systems.md). The university requirements and individual role justifications establish the academic scope and responsibility boundaries.

The scenarios assess single and batch checking, versioned inference/explanations, authorized history/statistics, feedback, permitted text contributions and operational interfaces. Their objectives are to demonstrate that invalid inputs fail safely, predictions obey the agreed interpretation contract, retained information is minimized, ownership is enforced and component failures do not produce fabricated predictions or false persistence confirmations. These observations support Proposal objectives O-05/O-06/O-08 and the interfaces to O-03/O-04/O-07; they do not establish user relevance or classifier quality.

The component path is browser UI -> FastAPI validation/authorization -> versioned preprocessing/inference, with PostgreSQL for permitted metadata. Restricted contributions, training data and model artifacts have separate access/lifecycle boundaries. Neither a public prediction nor an incorrect-result report starts training or activates a model. No test requires reading a phone inbox, opening a message URL or using private SMS.

Sanzhar leads inference/explanations, threshold/error analysis, FastAPI validation/privacy, persistence integration, API tests and Docker/CI/deployment. Rafael retains leadership of training/evaluation, baseline and model versions, history/statistics/feedback/retraining behavior and the general unit/E2E/load/adversarial test plan. Beknur retains leadership of data preparation/annotation, character features, React/TypeScript, multilingual/batch/history/feedback screens and UX/accessibility evaluation. Interface, fault and deployment cases here require their relevant participation; they do not transfer those leading responsibilities. All write their own technical documentation and tests; Beknur leads unified-report assembly.

No runnable API, frozen transport schema, executable dependency fixtures or application test environment is available in the reviewed baseline. All 96 scenarios below have execution status **Planned — Not Run**. Preconditions are not execution evidence. A mock's known answer can establish contract behavior only; natural-message quality and EV-01 require Rafael's separate evaluation. User comprehension and accessibility require Beknur's separate verification.

### 2. Test levels and proposed environment

| Level | Purpose and method | Boundary of the resulting evidence |
|---|---|---|
| Contract/schema | Validate versioned request, response and error definitions; compare approved examples and serialization allowlists | Requires an agreed schema; a schema alone does not establish running behavior |
| API input validation | Exercise the real request parser/validator with valid, invalid and boundary fixtures; inspect downstream call counts | Framework defaults are checked against the agreed policy |
| Authorization and privacy | Exercise owner/role rules and inspect stores, diagnostic sinks and temporary copies | An authorized response alone does not demonstrate absence of secondary retention |
| API integration | Connect the actual service to compatible preprocessing/inference and an isolated PostgreSQL instance | Database mocks or SQLite do not establish PostgreSQL-specific behavior |
| Mocked component interaction | Replace a dependency with a declared fixed fixture/fault stub to isolate correlation, error mapping or call ordering | Record each substituted boundary; no claim of full integration or model quality |
| Future end-to-end integration | Exercise the actual browser, API, model and database under declared origin/session settings | Sanzhar checks interfaces with Beknur and Rafael; this does not replace their UX or general E2E work |
| Fault injection and resource boundaries | Inject defined dependency failures and exercise agreed limits under controlled clocks/workloads | Capacity, availability and recovery claims require measured evidence and approved targets |

Use only synthetic fixtures and dummy owner/session identities in an isolated environment. Record the runtime, dependency/database/browser versions, test-runner version, service configuration and fixture hashes. Use a fixed compatible model artifact or explicitly named stub, with known preprocessing/interpretation versions and independently reviewed expected outputs. Disable unintended external message-URL access; use local network-call spies or controlled stubs. Capture ordinary logs, safe diagnostics, database changes and upload directories without exposing real credentials. Teardown must cover test stores, temporary copies and diagnostic artifacts under the agreed policy.

#### 2.2. Fixture and contract rules

- Keep a manifest of fixture IDs, synthetic origin, exact bytes/Unicode code points, normalization/privacy version, input interpretation and expected result/error. Parameterized variants remain part of their parent Test ID and must be individually accounted for at execution.
- Include EN/RU/KZ, mixed, undetermined, unsupported and transliterated cases. Use `en`, `ru`, `kk`, `mixed`, `und` and `other` consistently with the data strategy. Correct UTF-8 processing is separate from evaluated language coverage.
- Kazakh-specific characters, Russian `ё`, emoji and combining sequences need reviewed code-point and span oracles. Python and browser string-index units must be reconciled explicitly; matching a visually similar string is insufficient.
- Privacy fixtures use unmistakably synthetic canaries, non-live placeholders and reserved example addresses/domains. Do not use real phone numbers, passwords, authentication codes or conversations. A transient user-visible explanation may contain submitted synthetic fragments; the prohibited sinks are ordinary retained history/diagnostics and unauthorized disclosures. Consented restricted text is assessed against its separate policy.
- A CSV logical record can contain a quoted comma or newline. Freeze columns, quoting/encoding, maximum length units, file/body bytes, row limits and file-versus-row error rules under D-04/D-06 before generating boundary oracles.
- All HTTP-facing scenarios inherit **Expected status: Pending API contract (D-04)**. The reviewed contract must distinguish a valid prediction/result envelope from input/access errors and dependency failures. A mixed-row response may contain explicit row errors under that contract; it must not masquerade as all-row classification success. No particular HTTP code or route is approved by this plan.
- D-04 must define whether admission counts differ from completed predictions and how inference/persistence failures are counted. For a parseable file, independent expected logical-record counts must reconcile all recorded dispositions. An unparseable file needs an explicit file error rather than invented submission counts.
- Freeze a score-space/equality oracle under D-03. Do not add an arbitrary tolerance, threshold or confidence category. Any floating-point comparison tolerance must be justified by the chosen fixture/serialization and recorded before execution.

#### 4.3. Performance conditions

FLT-004 provides API-boundary measurements in coordination with Rafael's load strategy. D-06 must approve the workload and targets before acceptance: text-length distribution, single/batch mix, logical rows/file bytes, concurrency, arrival/duration model, warm-up, repetitions, stop conditions, worker/database budgets and limit policy. Record hardware/CPU/RAM, host/network placement, process count, dataset/fixture and model size/version, database state and dependency versions.

Measure client-observed response latency with a monotonic duration from request dispatch to complete response receipt. Declare any timeout/cancellation censoring and network effects. Separately instrument validation/preprocessing, inference, queue waiting and database work where available without logging SMS. Report p50/p95 with the calculation method and sample counts, completed requests per unit time, completed classified rows per unit time for batch work, unexpected failure rate, rejected/limited request counts and resource utilization. Do not combine row throughput with request throughput or hide failed/time-limited observations.

Report warm requests separately from cold initialization/readiness and any declared cold-request scenario. Keep intended negative-test outcomes distinct from unexpected service failures; declare all denominators. Compare distributions only under compatible profiles. Latency, throughput, error-rate, concurrency, time-window, memory and recovery acceptance values remain pending D-06/D-07; no capacity ranking or load result is established.

#### 4.4. Baselines and demonstration of objectives

For API correctness, the comparison oracle is the reviewed contract plus frozen synthetic golden fixtures, expected scoped records and known component outputs. It is not a learned statistical baseline. When an approved runnable implementation exists, its versioned contract/fixture outcomes can form a declared regression baseline; none is assumed to exist now. Fault variants compare the same fixture/environment with one recorded failure condition changed.

Rafael must define and substantiate the model baseline/candidate comparison and EV-01 evaluation conditions. The Dataset Strategy proposes an always-ham reference and TF-IDF classifier experiments; this API section neither selects a final baseline nor supplies its metrics. Existing commercial systems have no matched project benchmark here. Beknur must define the separate UX comparison/acceptance procedure from real user needs.

Achievement of O-05 requires version/score/explanation agreement plus actual error/threshold analysis; these cases contribute the interface evidence, not the whole analysis. O-06 requires actual single/batch/history/feedback integration with privacy/access evidence. O-08 requires genuine test, deployment and UX evidence across all owners. Model/data objectives additionally require real permitted corpora, pipeline/baseline reports and evaluation. The specification's final acceptance criteria remain authoritative.
